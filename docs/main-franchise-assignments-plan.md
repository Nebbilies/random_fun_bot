# Main franchise migration implementation plan

The [approved design](main-franchise-assignments-design.md) covers the assignment table, alias exclusions, and release verification. Production is on catalog v12 with the season schema, at commit 96794da when checked. The CSV import follows this release.

## 1. Write the focused regressions

- In [mainFranchiseCatalog.test.js](../test/mainFranchiseCatalog.test.js), keep an exact legacy column fixture. Exercise supported predecessors with and without season tables, populated and empty assignments, fresh creation, read-only rejection, rollback after the copy, and the second startup. Extend the concurrent-start test to prove that only one writer upgrades the database and both observe the same complete assignments.
- In the same suite, verify that one character can have two main franchises, duplicate pairs and invalid references fail, and deleting a character or franchise clears its assignments. In a merge fixture, assign one character to both IDs and another to the source alone. Verify both end up with one assignment to the survivor and the effective member list follows the existing merge rules.
- In [franchiseCatalog.test.js](../test/franchiseCatalog.test.js), reproduce a split franchise name contributed by a linked title and a synonym. Verify that a normalized exclusion applies to both, search finds the intended franchise, an exclusion on one ID leaves another ID's alias usable, and the excluded franchise still resolves by its canonical display name. Exercise a manual re-add and compare effective memberships before and after the alias change.
- In [deploy.sh fixtures](../test/deploy.sh), exercise the column-based predecessor and require the backup before schema changes. Cover backup failure and upgrade failure before either service restarts. Retain coverage for the ready layout and the existing narrow upgrade path.

## 2. Implement the upgrade and preserve existing entry points

- In [catalogFinalSchema.js](../lib/catalogFinalSchema.js), define the strict junction table with the composite primary key, cascading foreign keys, and the reverse index. Use the new table in the canonical schema and keep exact recognition of the two legacy column layouts. Keep earlier recognized layouts and season definitions available to the strict validator. Derive the expected objects for a fresh and a migrated database from the same schema definitions.
- In [vaultFortuneUpgrade.js](../lib/vaultFortuneUpgrade.js), reuse the existing write-locked upgrade transaction. Recheck the exact predecessor after acquiring the lock. For a column database, create the table, copy the populated pairs, and compare the new pairs with their source in both directions before dropping the legacy index and column. Validate the target schema, references, and integrity in the same transaction. Older supported ranked schemas that lack any main-franchise storage can install the new table directly when their existing upgrade chain reaches that stage.
- In [catalogDb.js](../lib/catalogDb.js), route the existing writable startup and deploy gate through the same upgrader. Give read-only callers a migration-required error for a recognized predecessor. Validate the predecessor and target with the actual season layout. Keep unknown and partial schemas rejected. Keep the existing handling of fresh final-catalog creation and pre-ranking catalogs.
- In [catalogRankingMigration.js](../lib/catalogRankingMigration.js), make a fresh ranking cutover install the empty assignment table. Account for the new, purpose-built table in the unrelated-data preservation check and verify it starts empty. Keep the inspection of a previously completed ranking cutover read-only, including on the known column layout.
- Update column-dependent fixtures in [catalogRankingMigration.test.js](../test/catalogRankingMigration.test.js), [efficiencyPublication.test.js](../test/efficiencyPublication.test.js), and [soulmateReclaimUpgrade.test.js](../test/soulmateReclaimUpgrade.test.js). Verify publishing changes preserve assignments for existing UUIDs and give newly published characters zero assignments.

## 3. Implement franchise merge and lookup behavior

- In [franchiseCatalog.js](../lib/franchiseCatalog.js), transfer source assignments to the surviving ID before deleting the source, using the composite key to skip pairs already on the survivor. Reuse the existing merge transaction and preserve compatibility for legacy catalogs with no assignment table.
- In [franchiseLookup.js](../lib/franchiseLookup.js), use the shared name normalization to match each franchise's excluded aliases against its stored aliases, linked titles, and linked synonyms. Keep canonical names eligible even if the same normalized text appears in an exclusion row. The default franchise index feeds both live and cached bot lookup. The direct-only index continues to use curated labels from the existing membership relation.
- Use the existing alias modification and catalog revision behavior so caches rebuild after an exclusion or manual re-add. Lookup retains the existing minimum query length. Effective membership and anime links stay independent of the new assignments.

## 4. Put the backup in the existing release gate

- In [scripts/deploy.sh](../scripts/deploy.sh) and its existing [catalog check entry point](../lib/catalogDb.js), continue using the deploy lock and both stopped services. When the gate recognizes the column layout, use the native Node SQLite backup API to create a consistent copy in a unique durable location under the VPS backup directory. Validate it as a readable predecessor, confirm it has the same legacy assignments, and report its path before applying the migration. Use an awaited gate so backup errors stop the deployment. Recheck the layout and validate the target before restart.
- Keep ordinary deploys on the ready layout free of additional backup work. If the snapshot succeeds and the migration fails, keep the snapshot and surface the error through the existing stopped-services path.
- Before merge and deployment, rehearse against a consistent production copy on Node 22.23.2. Run the deploy gate twice, exercise startup against the migrated copy, and compare the unrelated schema and data, including season records, character identities, effective memberships, catalog revisions, and SQLite sequences. Use a separate populated fixture to prove the column values migrate when present. Record backup and migration timings. Reopen a copy of the backup with the previous release to prove recovery.
- Before services resume writes, a committed migration can be rolled back with the verified snapshot and matching previous code. If services have resumed writes, diagnose and repair forward to preserve those writes. Any later reverse migration would require a verified conversion and at most one assignment per character.

## 5. Verification and handoff

Run the focused catalog and franchise suites first. On the pinned runtime, run npm test, npm run typecheck:catalog, bash -n scripts/deploy.sh, and bash test/deploy.sh. Use Git Bash on Windows when the default shell points to WSL. Review the diff and the rehearsal results before the deployment that automatically follows a merge to main.

On production, confirm the schema gate recorded its backup, the assignment table is present with the expected migrated pairs, the legacy column and index are gone, season data is readable, and both services pass their existing readiness checks. Recheck the new search behavior with the split-name fixture from rehearsal. Carry the reviewed franchise ID map and CSV import into the follow-up operation.
