# Season implementation plan

Work on `feature/season` against the [approved design](season-design.md). Keep the approved profile fields. Phase 4 starts with failing tests for each slice, then phase 5 implements the changes below. Phase 6 runs the verification matrix.

## 1. Install the season schema

- Add the season schema in `lib/seasonSchema.js`. Store one current season and settings per guild, roster membership, reminder or start delivery state, the one-use soulmate waiver, versioned profile summaries, and progress for pruning closed-season data. Use unique guild and season constraints for a scheduled rollover, profile snapshots, and delivery work.
- Extend `lib/catalogFinalSchema.js`, `lib/vaultFortuneUpgrade.js`, and `lib/catalogDb.js` through the existing v12 schema extension path. Recognize the reviewed predecessor and install the extension under the first-start write lock. Recheck after obtaining the lock so bot and portal can open the same database concurrently. Use the authoritative schema for fresh final catalogs and validate both the upgraded schema and its marker. Keep read-only opening and historical migration fixtures working without broadening the schema checks.
- In the upgrade transaction, initialize Season 0 from the union of guild-scoped gameplay evidence. Seed players from surviving ownership, affection, wish, allowance, event, or item records, using indexes and avoiding historical event replay. Do not use global configuration or catalog rows as evidence of play. Guilds without prior play acquire Season 1 on their first successful gameplay action.
- Record season identity on durable action and receipt roots that can outlive the cutoff. Give existing rows Season 0 semantics without replaying them. Reuse parent links for child rows. Update affected inserts to use explicit columns and preserve existing identifiers and counters.

## 2. Put the cutoff in gameplay transactions

- Add a season service and repository under `features/seasons/` for reading a guild's live season, recording participation, checking a captured season against that live season and its cutoff, and performing a guarded rollover. Reuse the catalog transaction helper. Perform the guard inside the transaction that would mutate gameplay, using the clock under the write lock. Early checks in Discord handlers can give immediate feedback while the transaction is the final check.
- Cover the durable roll, claim, publication, and legacy refund paths in `lib/characterRolls.js`, `features/rolls/rollLifecycleService.js`, its repository, `lib/rollDelivery.js`, and the allowance service and repository. Make row lookups and recovery queries respect the stored season. Record participation when a roll or claim succeeds.
- Cover ownership mutations in `lib/characterMarriage.js`, `features/trade/tradeService.js`, and wish mutations in `lib/characterWishlist.js`. Carry the season that opened the interaction through `commands/divorce.js`, `commands/wish.js`, `commands/soulmate.js`, and `features/trade/tradeRuntime.js`. Include both players in successful transfers. Reject outdated controls with the existing expired-interaction response. Clear guild-local trade reservations after the rollover commits.
- Guard item activation and settlement, timed actions, escape and mystery transitions, vault interactions, reward delivery, and affection earning at their existing write boundaries. Review `lib/itemActivation.js`, `lib/itemActions.js`, `lib/itemActionRuntime.js`, `lib/characterRollRuntime.js`, `lib/mysteryRuntime.js`, `lib/mysterySessionState.js`, `lib/vaultSessions.js`, `lib/vaultRuntime.js`, `lib/vaultRewards.js`, `lib/characterAffection.js`, and `lib/affectionRewards.js`. Audit entry points that release a hold or refund usage after an awaited Discord operation. A reply captured in the closing season cannot affect the next one even if the same marriage continues.
- Apply the same check to portal item grants and global roll/claim adjustments in `web/reviewCharacterTags.js` and the allowance service. While a guild is at cutoff, global controls can apply to eligible guilds and report any guilds they skipped. Leave catalog moderation and unrelated bot features independent.

## 3. Apply and archive one rollover

- In `lib/profileCardData.js`, extract the transaction-neutral projection for the approved profile fields and reuse it for both live and archived cards. Reuse the count leaderboard ordering in `lib/serverLeaderboard.js`. Share its fresh member lookup for cutoff and reminder batches. Wait outside the SQLite write transaction for a complete result. Treat a successful absence as a departure and retry incomplete lookups for the affected guild.
- Once the cutoff is due, take the union of closing roster members and relevant ownership candidates for the membership lookup. Recheck the queued rollover revision, guild, season, and due time in one guarded transaction. Save a versioned snapshot for every closing player, including departed and late-joining players, using closing stats and pre-reduction soulmate affection.
- Release restrictive live dependencies before touching inventory or marriages. Inspect `lib/itemExpirySchema.js`, `lib/vaultFortuneSchema.js`, `lib/itemActionStorage.js`, and `lib/characterOwnershipHistory.js`. Remove open reservations and deactivate pending effects for the closing guild. Clear inventory, capacity upgrades, buffs, protection locks, wishes, puzzle wins, claim/roll/daily usage, and prior ownership losses. Handle the ordinary marriage loss trigger so the wipe cannot populate Chronicle of Return. Preserve guild item discoveries and existing shared data.
- Preserve eligible soulmate marriages, replace their affection with the rounded-down tenth, reset switch cooldown, and add their owners to the new roster. In `lib/characterAffection.js`, consume the reminder waiver only after a valid switch would otherwise fail cooldown. Share the normal milestone definition and selection path for the new-season starting reward. Clear old entitlements and include the active season in new milestone reward identifiers so each milestone pays at most once for that relationship and season. Use `lib/affectionRewards.js` and the existing direct reward settlement path for normal inventory charges, expiry, and notification.
- In the same transaction, advance the guild's current season, record the completed rollover, and persist pending start-announcement work. A retry returns the recorded result. Full rollback preserves the old season, its live state, and its scheduled cutoff. Run Discord sends and edits after commit.

## 4. Retire and prune old gameplay records

- Update `lib/catalogRuntimeRecovery.js`, `lib/gameRecovery.js`, and affected domain recovery queries to ignore retired gameplay roots. Apply season checks to old interaction IDs before looking up an active object with a similar key. Preserve validators for current records, including recovery proof and idempotency.
- Add a small pruning routine under `features/seasons/`. After rollover, delete dependency groups in bounded transactions, with active season and guild checks on each batch. Follow `lib/catalogRuntimeSchema.js`, `lib/itemRewardSourceSchema.js`, `lib/affectionRewardSchema.js`, and `lib/vaultFortuneSchema.js` for child relationships. Cover roll notices and deliveries, mystery and vault records, item actions and costs, and affection source, decision, award, and reward receipts. Keep any minimal proof that an active replay path still references until it becomes safe to delete.
- Persist the work needed to retry after restart. Keep bulk deletion outside the cutoff transaction. Measure free pages and writer contention on a disposable database and leave physical file compaction to separate maintenance.

## 5. Wire the portal and Discord scheduler

- Add season controls to `web/reviewGame.html` and `web/assets/reviewGame.js`. Add a route handler in `web/reviewSeasons.js` under the existing admin-only `/api/game` namespace via `web/reviewCharacterTags.js`. Support guild status, settings, channel validation, schedule preview, confirmation, and cancellation. Reuse portal auth, Origin and CSRF handling, and revision checks. Show the 30-day target, planned times, channel errors, and delivery progress. Display the exact guild and season numbers before confirmation.
- In `lib/gameConfig.js`, compare the before and after effective claim schedule for scheduled guilds, including those that inherit global rules. Recompute a queued rollover's times when applicable. Refuse schedule edits that would move an announced cutoff. Preserve the immediate claim reset as its own operation.
- Add the bot worker under `features/seasons/` and wire it into `app/bootstrap.js` and `app/recoveryWorker.js`. Reuse `nextClaimReset` to compute consecutive claim boundaries. Wake up for due jobs and use periodic recovery to discover portal changes and retry work. Process overdue cutoff checks before regular recovery can change the affected guild, including before startup roll recovery. Keep unrelated guilds available.
- Validate the configured channel with the existing Discord client before accepting a schedule. The bot needs permission to view the channel, post, and read message history to verify an uncertain send. Persist a claim for reminder delivery before sending. Reconcile an uncertain send with its durable delivery identity before rescheduling or canceling. At its planned cutoff, hold only the affected guild while resolving a possibly posted reminder. If the public reminder was posted, keep its advertised time. If Discord confirms no reminder posted, requeue for a later window. Track each bounded, explicitly allowed mention batch. A failed batch can be retried without changing an announced cutoff.
- Queue the new season announcement at commit and reuse stable Discord delivery identifiers and message receipts for both announcements. Use the guild's current prefix in reminder instructions. Report errors through the portal and resume delivery on restart.

## 6. Add the season select to the profile

- Extend `commands/profile.js` and `lib/profileCardData.js` to load current and historical data for the invoking guild and user. Add a string select in an action row beneath the existing embed. Label the selected season, list completed seasons newest first, and page the choices once the select limit is reached. Keep the current season accessible.
- Reuse the existing PNG renderer and portrait preparation. On selection, check the requester and guild, acknowledge the component, and replace the image attachment on the same reply. Serialize updates so a slower render cannot overwrite a newer choice. Route expired controls through `app/events/interactionCreate.js` and cover unavailable fields when reading an earlier summary version.

### Cutoff rehearsal results

The final local rehearsal used a 386 MiB synthetic WAL database with 1,328 marriages, 33 players, and 49,000 archived gameplay receipts. The cutoff transaction took about 1 second while another connection wrote to a different guild. It saved 33 profiles and carried over 16 soulmates with reduced affection and their starting item. The rehearsal reopened the database during pruning and verified the archived profiles, the other guild's state, runtime restart validation, and foreign key integrity.

Pruning used batches of 200 records and deferred 38 attempts while another writer held the database. It reclaimed about 385 MiB of reusable SQLite pages. These measurements reflect the synthetic data and local load. The Discord rollout tests used fake transport.
